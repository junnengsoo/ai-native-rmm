# Windows endpoint contract — slice 1

This is a manually launched endpoint agent and independent test peer, not a
control plane, enrollment flow, installer, or customer deployment. The harness
listens on Windows loopback; the agent initiates WSS. This verifies the transport
and real worker but does not prove cross-machine networking/NAT traversal.

## Authentication

The agent uses a nonexportable private key in the launching account's Windows
CurrentUser/My certificate store. Configuration carries a certificate thumbprint,
the SHA-256 fingerprint of the expected server certificate, a device identity,
and a WSS URL. Thumbprints and fingerprints are public identifiers. Mutual TLS
proves possession on each connection; both peers require an exact pinned
certificate and check validity dates. Pinning is the trust policy, not a
test-only bypass of certificate checks. The harness generates separate one-day
test identities; no production credentials are involved. Production enrollment
and rotation must provision/update the pins in later slices.

The worker receives a restricted environment and no key configuration. It runs
under the launching account, so arbitrary scripts can still exercise that
account's privileges and access its certificate store. A process boundary is
not a sandbox. This harness is only for the isolated authorized Windows VM.

## Wire boundary

UTF-8 JSON text messages, one object per WebSocket message. Protocol version 1
uses dispatch messages such as `hello`, `open_session`, `execute`,
`cancel_execution`, and `close_session`; endpoint lifecycle/output evidence is
returned as ordered `ledger_batch` records and committed by the peer with
`ledger_ack`. `rejected` reports malformed, duplicate, busy, or
reconciliation-pending dispatch. Device/session/execution IDs and script hashes
are bound to the relevant dispatch and ledger records. Scripts carry their
exact UTF-8 SHA-256 hash; a mismatch is rejected before invocation. Only one
session and invocation are allowed. Unknown fields/types and invalid bounds are
rejected. The harness implements the peer independently and sends the same wire
contract as a future control plane.

Lifecycle is generated by execution machinery on a private local pipe, never
parsed from script stdout/stderr. Output is data; consumers must render it
inertly. Completion means invocation completion, not that an IT issue is fixed.

`output_chunk` ledger records carry `stream` (`stdout` or `stderr`) and inert
text chunks while an execution is still running. The terminal
`execution_finished` record carries `state`, `invocationOutcome`, `exitCode`,
`hadErrors`, `durationMs`, `captureTruncated`, and `lastNativeExitCode`,
alongside the resource bindings. Terminal results do not include stdout/stderr
previews; output text is carried only by ordered output records. A native exit
value is evidence about the last native command, not a universal script outcome.
`LASTEXITCODE` is reset before every invocation. Ordinary and nonterminating
error completion normalizes to 0; an unhandled terminating error normalizes to
1. Explicit exit reports its requested code. Explicit exit deliberately retires
the worker: close the old session and open a fresh one before further execution.
The native worker host observes PowerShell's
[`PSHost.SetShouldExit`](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.host.pshost.setshouldexit?view=powershellsdk-7.4.0)
callback; it does not infer explicit exit from a native command's exit value.
The endpoint launches a private 64-bit Windows PowerShell `Desktop` worker
process through `NativePowerShellWorker.ps1`; Windows tests gate changes to
those native engine semantics.

The wire format still accepts bounded `timeoutMs` values for compatibility, but
the agent does not enforce a separate per-execution deadline. Authenticated
`cancel_execution` and `close_session` requests stop the active worker.
The endpoint continuously drains PowerShell output and writes UTF-8-safe chunks
bounded to 8 KiB of text bytes into the local ledger before JSON framing. The
control plane derives terminal API previews and 64 KiB pages from durably stored
output records.
Preview shortening is not capture loss. A session worker is owned by a
Windows Job Object. Cancellation or closure terminates that job,
including owned child processes and waits up to 30 seconds for confirmation;
only confirmed zero active processes permits confirmed stopping. Stopping never
undoes filesystem, registry, network, or other script side effects.

## Run from macOS

Prerequisites: Azure CLI authenticated to the subscription containing the running
`rmm-trial-win11/rmm-win11` VM; .NET 8 SDK installed at `C:\rmm-test-runtime` on
that VM. No Linux VM or Python control plane is required. No SSH/RDP/public IP
is needed. From this worktree:

```sh
bash scripts/azure-smoke.sh
```

The wrapper archives this checkout's source, deploys it to a unique directory
under Windows Temp, and starts `scripts/windows-smoke.ps1` using Azure RunCommand.
That script builds the binaries, creates isolated nonexportable certificates,
starts the harness which launches the agent, and removes the test certificates
and private keys afterward. Azure is only the deployment/test launcher: scripts
to investigate the device are sent by the harness across the authenticated WSS
connection. The executable can also be launched manually with the documented
public arguments. Retained source/build files under Temp contain no private keys.

From a Windows checkout with .NET 8 on PATH:

```powershell
.\scripts\windows-smoke.ps1
```

The suite also runs an independent reachability peer for [slice 2](enrollment.md).
Run it elevated on the isolated test Windows machine: it temporarily trusts its
unique test server certificate in the machine Root store, checks actual CNG
signing/nonexportability, pending reconnect,
heartbeat cadence and refusal of execution, then removes that trust and test key.
The original mTLS worker scenarios and their trust policy remain unchanged.

Expected: `SMOKE` shows a correlated `completed_normally`, exit 0 terminal
record; the harness verifies `hello from Windows` arrived in preceding output
records. `SMOKE_ERROR` shows `terminating_error`, exit 1; the harness verifies
`expected-smoke-error` arrived in stderr output records. The four scenario PASS
lines and final `RMM_SUITE_PASSED` mean the full suite passed. The shell wrapper
exits nonzero if that marker is absent, even if Azure reports the extension
invocation itself succeeded. Expected negative-authentication attempts print
only sanitized exception categories; no key/configuration dumps are emitted.

The agent's manual entry point, when a trusted peer and certificates are already
configured, is:

```powershell
dotnet src/EndpointAgent/bin/Release/net8.0/EndpointAgent.dll --agent wss://localhost:18443/agent ENDPOINT_CERT_THUMBPRINT SERVER_CERT_SHA256 test-device
```

## Recorded verification and limitations

The most recent recorded real-Windows run for this harness was on 2026-09-21,
before the issue-10 rebase and before the native worker-mode restoration in this
branch. For the current issue-10 pass, the harness source and endpoint project
were build-checked locally, but a fresh authorized Windows VM smoke was not run
in this environment. The recorded 2026-09-21 run used the existing Windows 11 VM
with .NET SDK 8.0.425 and the previous hosted PowerShell 7.4.13 worker:

- Invocation and persistent session: stdout/stderr output frames and
  correlation, terminal result metadata without duplicated output previews,
  terminating and nonterminating errors, native exit 7 separated from normalized
  0, no stale LASTEXITCODE, variables/functions/directory persistence, printed
  fake lifecycle kept as data, disclosed capture truncation, explicit exit 23
  and 0, and fresh state after replacement.
- Authentication, validation, and ledger transport: wrong endpoint key and server
  pin rejected, nonexportable endpoint key, dummy secret/configuration excluded
  from worker, altered hash, wrong device/session, unknown fields, invalid
  timeout field and malformed JSON rejected, duplicate dispatch did not repeat its
  counter side effect, and ledger batches were acknowledged only after the
  harness accepted their ordered records.
- Reconnect behavior: an active invocation survived socket replacement, later
  returned an ordinary terminal ledger record, and the same session remained
  usable after normal completion.
- Active close and worker loss: output received before active close retained,
  confirmed `cancelled`/`stopped` with the session closed, native child
  confirmed gone, no reuse of retired workers, and abrupt worker exit recorded
  as `outcome_unknown`.

The manual harmless/error smoke also ran in that suite (about 157 ms and 16 ms
of measured invocation time in the recorded run). These are invocation timings,
not a cross-network latency claim. The same external-behavior suite runs in the
Windows GitHub Actions job.

Reconnect reconciliation is ledger replay, not script replay. The endpoint keeps
an append-only local ledger plus an atomic acknowledgement checkpoint; after
reconnect it resends records above that checkpoint. Normal terminal records
materialize as ordinary execution results and leave the session worker reusable.
Cancellation, active session close, explicit exits, and worker loss retire the worker
truthfully through ledger records. Scripts are limited to 32,768 code units,
connect waiting to 15 seconds, and idle frame waiting to two minutes.
Cancellation/cleanup and worker-loss results conservatively disclose possible
capture loss. Output is UTF-8 chunked into ledger records before transport.
Success output is string rendered from PowerShell objects; debug/verbose/progress
streams are drained but not retained. Later service lifecycle slices remain
separate. Job cleanup covers inherited worker descendants, not services,
scheduled tasks, or other work that privileged scripts deliberately create
outside that ownership.
